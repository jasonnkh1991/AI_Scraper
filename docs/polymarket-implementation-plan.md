# Polymarket Probability Radar Implementation Plan

Last updated: 2026-06-14 HKT

## 0. Objective

Build a separate Polymarket monitoring pipeline for investment-relevant probability shocks.

This is not a replacement for the existing X/Twitter scraper. It is a second signal layer:

```text
X scraper = what people/news accounts are saying
Polymarket radar = what prediction-market money is repricing
```

Primary output:

```text
POLYMARKET SIGNAL
A market probability moved sharply with enough volume/liquidity to matter.
```

Secondary output:

```text
POLYMARKET DIGEST
A short summary of major probability shifts across monitored markets.
```

## 1. Non-Negotiable Safety Boundary

This feature must be additive. It must not break the existing AI_Scraper system.

Do not change these in Phase 1:

- `crawler.py` X/Twitter fetching logic
- existing `tweet_queue` behavior
- existing AI tweet scoring schema
- existing X digest schedule
- existing Telegram X alert threshold
- existing `/study` behavior
- existing `.github/workflows/monitor.yml`

Implement Polymarket as a parallel pipeline:

```text
polymarket_monitor.py
.github/workflows/polymarket.yml
Supabase polymarket_* tables
```

If Polymarket fails, X monitoring must continue normally.

## 2. Why Auto-Discovery Is Required

A fixed Polymarket watchlist will miss new markets when the market narrative changes.

Examples:

- a new Fed chair candidate appears
- a new Iran ceasefire market appears
- Trump announces a new tariff topic
- a new Nvidia / OpenAI / Tesla catalyst becomes tradable
- crypto regulation event appears suddenly

So the design needs both internal and external discovery:

```text
Core Watchlist = stable, curated, low-noise markets
Polymarket API Discovery = new Polymarket markets from volume/search/tag data
External Narrative Discovery = new terms from X/news/Apify context, then reverse-search Polymarket
```

The first implementation should include external narrative discovery. API-only discovery is not enough because it can miss new language before it appears in our static keyword list.

Recommended first version:

```text
Core watchlist: 30-40 markets
Polymarket API discovered markets: up to 15 markets
External narrative discovered markets: up to 15 markets
Total active monitored markets: 50-70
```

## 3. Data Sources

Use Polymarket public APIs for market data and use external content only for discovering new search terms.

Polymarket docs state market data is available through public REST endpoints with no API key, authentication, or wallet required.

Useful Polymarket API families:

- Gamma API: events, markets, public search, tags, series
- CLOB API: prices, order books, spread, midpoint, price history
- Data API: open interest, holders, trades, activity

MVP market data should use:

```text
Gamma API /events and /markets for discovery and market metadata
Gamma market outcomePrices for implied probability
CLOB spread / book only for higher-quality signal validation
```

External narrative discovery should use existing or low-cost sources:

```text
X scraper outputs already stored in Supabase
high-priority pending tweets
Telegram/study-only clusters
selected Apify/X/news searches only when there is a new dynamic term or market shock
```

Do not scrape external content on every run by default. Use it as a controlled discovery layer, otherwise Apify cost and noise will rise quickly.

Avoid trading endpoints. This is a read-only monitoring tool.

## 4. Supabase Schema

Create new tables only. Do not modify existing production tables.

### 4.1 `polymarket_markets`

Purpose: active markets we monitor.

Suggested columns:

```sql
id bigint generated by default as identity primary key,
market_id text unique,
condition_id text,
event_id text,
slug text,

created_at timestamptz not null default now(),
updated_at timestamptz not null default now()
```

### 4.2 `polymarket_snapshots`

Purpose: compact market state at each polling time.

Important: do not store full `raw_json` by default. It will bloat Supabase quickly.

Suggested columns:

```sql
id bigint generated by default as identity primary key,
market_id text not null,
condition_id text,
yes_price numeric,
no_price numeric,
volume numeric,
volume_24hr numeric,
liquidity numeric,
spread numeric,

```

Indexes:

```sql
(market_id, snapshot_at desc)
(snapshot_at desc)
```

Retention:

```text
Keep 30 days by default.
If Supabase free DB size becomes tight, reduce to 14 days.
```

Retention:


## 5. Market Selection Design

### 5.1 Core Watchlist

Manual seed markets by topic:

```text
Fed / rates / macro: 10-15
Trump / tariff / US policy: 10-15
Geopolitics / oil / war: 10-15
Crypto / regulation: 8-12
AI / Nvidia / Tesla / OpenAI / tech: 8-12
Elections / political control: 5-10
```

Manual markets should have higher `watch_priority` and should not be removed by auto-discovery cleanup unless closed.

### 5.2 Discovery Term Sources

Initial static keyword groups:

```python
POLYMARKET_DISCOVERY_KEYWORDS = [
    "fed", "fomc", "rate cut", "interest rates", "powell", "fed chair",
    "trump", "tariff", "china", "taiwan", "sanctions", "export controls",
    "iran", "israel", "ceasefire", "hormuz", "oil", "ukraine", "russia",
    "bitcoin", "ethereum", "crypto", "sec", "etf", "stablecoin",
    "nvidia", "tesla", "openai", "xai", "ai", "semiconductor",
]
```

Dynamic term sources must be included from day one:

```text
1. Existing `dynamic_watch_terms` learned by the X pipeline
2. High-priority pending tweets in `tweet_queue`
3. Recent `event_clusters` with impact >= 7
4. Recent `telegram_alerts` / study-only signals
5. Optional Apify/X/news enrichment when a new term appears repeatedly or with high priority
```

The term extractor should keep:

```text
person names: Kevin Hassett, Scott Bessent, Jensen Huang
products: Vera Rubin, Blackwell Ultra, Stargate
places/events: Hormuz, Taiwan Strait, ceasefire, tariff package
companies/tickers: NVDA, TSLA, OpenAI, xAI, Nebius
policy phrases: Fed chair, export controls, stablecoin bill
```

### 5.3 Auto-Discovery Sources

Use these in order:

1. Gamma `/events?active=true&closed=false&order=volume_24hr&ascending=false&limit=100`
2. Gamma `/markets?active=true&closed=false&order=volume_24hr&ascending=false&limit=100`
3. Gamma `/public-search?q=<keyword>` for static and dynamic topic-specific discovery
4. Existing X pipeline dynamic terms from Supabase state
5. Apify/X/news external search only for high-priority new terms or unexplained Polymarket probability shocks
6. Tag-based discovery after we map useful tag IDs

### 5.3.1 External Narrative Discovery Loop

This loop is required in the first implementation, but it must be cost-controlled.

```text
Step 1: Read latest dynamic terms from X pipeline and recent high-impact clusters.
Step 2: Build a compact search term list, capped at 20 terms per run.
Step 3: Search Polymarket public-search for each term.
Step 4: If Polymarket has matching active markets with volume/liquidity, add to `polymarket_markets`.
Step 5: If no matching market but term is high-priority, optionally run Apify/X/news enrichment no more than a configured daily cap.
Step 6: Feed enriched terms back into Polymarket public-search.
```

Suggested external discovery caps:

```text
POLYMARKET_EXTERNAL_DISCOVERY_ENABLED=true
POLYMARKET_EXTERNAL_TERM_LIMIT=20
POLYMARKET_EXTERNAL_APIFY_DAILY_MAX_RUNS=4
POLYMARKET_EXTERNAL_APIFY_MAX_CHARGE_USD=0.02
POLYMARKET_EXTERNAL_TERM_TTL_HOURS=72
```

This lets us use Apify only for targeted blind-spot reduction, not broad scraping.

### 5.4 Auto-Discovery Filters

A market is eligible only if:

```text
active = true
closed = false
question matches investing keyword / tag
volume_24hr >= configurable minimum
liquidity >= configurable minimum
end_date is not already expired
not obviously sports / entertainment / celebrity noise
```

Initial thresholds:

```text
POLYMARKET_DISCOVERY_MIN_VOLUME_24H = 5000
POLYMARKET_DISCOVERY_MIN_LIQUIDITY = 2000
POLYMARKET_API_DISCOVERY_MAX_MARKETS = 15
POLYMARKET_EXTERNAL_DISCOVERY_MAX_MARKETS = 15
```

### 5.5 Discovery Score

Score each discovered market:

```text
score = keyword relevance
      + log(volume_24hr)
      + log(liquidity)
      + recency bonus
      + category bonus
      - entertainment/sports penalty
      - low liquidity penalty
      - near-expiry noise penalty
```

Only top N auto-discovered markets remain active.

## 7. Probability Shock Detection

Compare latest snapshot with prior snapshots:

```text
15m window
1h window
6h window
24h window
```

Initial alert thresholds:

```text
15m move >= 8 percentage points
1h move >= 12 percentage points
6h move >= 20 percentage points
24h move >= 30 percentage points
```

Quality gates:

```text
min liquidity >= 2000
min volume_24hr >= 10000
max spread <= 0.08
market not closed
```

Only send Telegram if:

```text
quality_score >= 70
or probability_change >= 20 percentage points with liquidity >= 2000
```

## 8. Quality Score

Suggested scoring:

```text
quality_score = 0
+ probability_move_score
+ volume_score
+ liquidity_score
+ orderbook_score
+ topic_relevance_score
- spread_penalty
- thin_market_penalty
- near_expiry_penalty
```

Example:

```text
+30 if 1h move >= 12 pts
+20 if volume_24hr >= 50k
+20 if liquidity >= 10k
+10 if spread <= 3 pts
+10 if topic maps to macro/tech/geopolitics/crypto
-20 if spread > 10 pts
-20 if liquidity < 2k
```

## 11. Cost Estimate

### 11.1 Direct API Cost

Polymarket market data API: expected $0/month for public REST reads.

No Apify is required for Polymarket market data itself.
Apify may be used only for capped external narrative discovery.
No OpenAI required in MVP.

### 11.2 GitHub Actions Cost

If repository remains public and GitHub Actions free public-runner policy remains available, expected fixed cost is $0/month.

Runtime estimate:

```text
96 runs/day * 30 days = 2,880 runs/month
```

If each run takes 20-45 seconds:

```text
Low: 2,880 * 20s = 57,600s = 960 min/month
High: 2,880 * 45s = 129,600s = 2,160 min/month
```

This is fine for public repos, but would matter if the repo became private or GitHub changed policy.

### 11.3 Supabase Storage Cost

Main cost/risk is database size, not API cost.

Assume:

```text
80 markets
96 snapshots/day
30 days
= 230,400 snapshot rows/month
```

How the estimate is derived:

```text
snapshot row = ids/question reference + 8-10 numeric fields + timestamptz
Postgres tuple/header/null bitmap/alignment overhead
plus btree index entries on (market_id, snapshot_at) and snapshot_at
plus Supabase/Postgres page overhead and TOAST risk if text columns are long
```

Lean snapshot, no raw_json and short market_id/question handling:

```text
~0.7KB-1.5KB per row including index overhead
230,400 rows * 0.7KB = ~161MB
230,400 rows * 1.5KB = ~346MB
```

Conservative estimate:

```text
~2KB per row
230,400 rows * 2KB = ~461MB
```

Bad design, full raw_json stored:

```text
~5KB-20KB per row
230,400 rows * 5KB = ~1.15GB
230,400 rows * 20KB = ~4.6GB
```

Important Supabase constraint:

```text
Supabase free tier database size is commonly treated as ~500MB.
So 80 markets with 30-day retention can be too close to the limit.
```

Conclusion:

```text
Do not store raw_json by default.
Do not store long question text on every snapshot if avoidable.
Use market_id foreign key/reference and keep full question in `polymarket_markets`.
Use compact numeric snapshots.
Add retention cleanup from day one.
14-day retention is safer than 30-day retention on Supabase free tier.
```

Safer first version storage target:

```text
60 markets * 96 snapshots/day * 14 days = 80,640 rows
At 0.7KB-1.5KB/row = ~56MB-121MB
At 2KB/row = ~161MB
```

This is much safer for Supabase free tier.

### 11.4 Telegram Cost

Telegram Bot API: expected $0/month.
